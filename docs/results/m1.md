## Quality control (DMAIC)

| Phase | This repository |
|---|---|
| Define | Developers and on-call engineers need to know, before merging, whether a migration will block a large PostgreSQL table, and a way to rename or retype a column without breaking running code. CTQs and targets are in [RFC 0001](../rfc/0001-design.md). |
| Measure | 35 statement forms run on PostgreSQL 17.11 with `pg_locks` and `relfilenode` read back; 58 rule cases; an expand/contract run with concurrent writers; a 100,000-row CLI run. |
| Analyze | All 35 predictions matched on the first server run. Two problems were found while building: the concurrent-writer test could finish its backfill before the writer connected (fixed by waiting for 20 writes first), and the CLI's `attempts` counter really counted transactions (renamed). The backfill guard in the trigger is required: without it the backfill copied `lower(email)` back into the old column (mutation 10 in the quality doc). |
| Improve | Plans emit only statements that pass the analyser on a 500-million-row table; NOT NULL is added through a validated check; batches are resumable and serialised by an advisory lock. |
| Control | CI: `make ci` (gofmt, vet, tests with `-race`), `make audit` (govulncheck), and a `postgres` job running every test against `postgres:17.11` that fails if any test skips. `osm analyze` exits 1 on danger, so it can gate a migration directory in any CI. Strict spec validation (unknown fields, identifier pattern) is the poka-yoke for the runner. |

## What is CI-only or not measured

- The race detector (`-race`), and the tests against the `postgres:17.11` container: written, not
  run yet (no push).
- Lock waits and error rates under load (M3), trigger overhead per write, replication lag (M2).
- `CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY` and `VACUUM FULL`
  cannot run inside a transaction, so their rules come from the documentation and are not checked
  against the server.
